# REST API Reference

The Nexus Repository Manager exposes a comprehensive REST API for managing repositories, security, and administration. This document serves as the central index for all API endpoints, authentication mechanisms, common patterns, and error handling conventions.

- **Management API endpoints** are served under the `/service/rest/v1/` base path.
- **Format-native protocol endpoints** are served under `/repository/{repo_name}/` for most formats, or `/v2/{repo_name}/` for Docker.
- **OpenAPI 3.x documentation** is auto-generated by flask-smorest and accessible at `/swagger.json` when the application is running.

### Repository Management

CRUD operations for repositories, components, and assets. Includes format-native protocol handlers for Maven, npm, Docker, NuGet, PyPI, APT, and Raw formats. Provides content search (full-text indexing backed by Whoosh or Elasticsearch) and browse tree navigation for hierarchical component/asset traversal.

See [repositories.md](repositories.md) for the complete endpoint reference.

### Security Management

User, role, and privilege management with a three-tier RBAC model. SSL/TLS certificate lifecycle management (PEM/PKCS12 import/export). Content Selector Expression Language (CSEL) for sub-repository access control. API key generation for CI/CD pipeline authentication. Audit log retrieval with structured JSON events.

See [security.md](security.md) for the complete endpoint reference.

### Administration

Health monitoring with individual component checks (database, BlobStore, scheduler) and aggregated system status. Scheduled task management with cron-style scheduling via APScheduler. Diagnostic support ZIP generation with automatic credential redaction. Hierarchical system configuration management with type validation and change notifications.

See [admin.md](admin.md) for the complete endpoint reference.

## Authentication

The API supports multiple authentication methods, evaluated in order by the multi-realm authentication chain:

1. **HTTP Basic Authentication** — Username and password credentials via the `Authorization: Basic <base64>` header.
2. **Bearer Token (API Key)** — API keys for CI/CD pipeline authentication via the `Authorization: Bearer <api-key>` header (F-304).
3. **JWT Token** — JSON Web Tokens via the `Authorization: Bearer <jwt>` header or cookie-based session tokens.
4. **LDAP** — Federated authentication against LDAP/Active Directory servers.
5. **SAML/OpenID Connect** — SSO federation with external identity providers.

### Authentication Flow

The authentication chain follows the **"First Successful"** pattern (replaces Apache Shiro 2.0.0):

1. Credentials are extracted from the request (Authorization header, form data, or cookies).
2. Each authentication realm is tried in order until one succeeds or all fail.
3. On success, the authenticated user principal is attached to the request context via Flask-Login.
4. On failure (all realms exhausted), a `401 Unauthorized` response is returned.

```
Request ──► Extract Credentials
                │
                ▼
          Local Realm (bcrypt password check)
           ├── success ──► RBAC Evaluation
           └── fail
                ▼
          Bearer Realm (API key validation)
           ├── success ──► RBAC Evaluation
           └── fail
                ▼
          JWT Realm (PyJWT token decode)
           ├── success ──► RBAC Evaluation
           └── fail
                ▼
          LDAP Realm (python-ldap bind)
           ├── success ──► RBAC Evaluation
           └── fail
                ▼
          SAML/OIDC Realm (SSO federation)
           ├── success ──► RBAC Evaluation
           └── fail ──► 401 Unauthorized
```

### Anonymous Access

- Unauthenticated requests are granted the `nx-anonymous` role by default.
- Anonymous access can be restricted or disabled per-repository via RBAC configuration.
- To fully disable anonymous access, remove all privileges from the `nx-anonymous` role.

### Authentication Examples

**HTTP Basic Authentication:**
```bash
curl -u username:password https://nexus.example.com/service/rest/v1/repositories
```

**Bearer Token (API Key):**
```bash
curl -H "Authorization: Bearer nxrm-a1b2c3d4-e5f6g7h8-i9j0k1l2" \
  https://nexus.example.com/service/rest/v1/repositories
```

**JWT Cookie-Based Session:**
```bash
# Login to obtain JWT cookie
curl -c cookies.txt -X POST https://nexus.example.com/service/rest/v1/security/login \
  -H "Content-Type: application/json" \
  -d '{"username": "admin", "password": "admin123"}'

# Use cookie for subsequent requests
curl -b cookies.txt https://nexus.example.com/service/rest/v1/repositories
```

## Authorization (RBAC)

Access control follows a three-tier Role-Based Access Control (RBAC) model:

### Tier 1 — System Privileges

Global permissions for administrative functions. Examples include `nx-all` (superuser access) and `nx-admin` (administrative functions). System privileges are evaluated first and grant access regardless of repository-level permissions.

### Tier 2 — Repository Permissions

Per-repository permissions assigned through roles:

| Permission | Description |
|------------|-------------|
| `read` | View and download repository content |
| `write` | Upload and modify repository content |
| `admin` | Manage repository configuration |

### Tier 3 — Content Selector Expression Language (CSEL)

Sub-repository path-based access control using CSEL expressions to match component paths and attributes. CSEL enables fine-grained permissions such as restricting a user to only access components within a specific namespace (e.g., `path =^ "/org/example/"`).

### Authorization Rules

- Authentication is **always** evaluated **before** authorization. This is a strict invariant.
- Unauthenticated requests to protected endpoints receive `401 Unauthorized` — never `403 Forbidden`.
- Authenticated but unauthorized requests receive `403 Forbidden`.
- Protected endpoints use Flask route decorators:
  - `@requires_auth` — Ensures the request is authenticated.
  - `@requires_role(name)` — Requires a specific role (e.g., `nx-admin`).
  - `@requires_privilege(type, resource)` — Requires a specific privilege on a resource.

## Common Request/Response Patterns

### Content Types

- All management API requests and responses use `application/json`.
- Format-native protocol endpoints use format-specific content types:

| Format | Content Type |
|--------|-------------|
| Maven POM | `application/xml` |
| Maven JAR | `application/java-archive` |
| npm packument | `application/json` |
| Docker manifest | `application/vnd.docker.distribution.manifest.v2+json` |
| NuGet package | `application/octet-stream` |
| PyPI package | `application/octet-stream` |
| APT package | `application/vnd.debian.binary-package` |

### Request Headers

| Header | Required | Description |
|--------|----------|-------------|
| `Authorization` | For protected endpoints | Authentication credentials (`Basic` or `Bearer`) |
| `Content-Type` | For POST/PUT requests | Request body format (typically `application/json`) |
| `Accept` | Optional | Desired response format |
| `X-Request-Id` | Optional | Client-provided request correlation ID for tracing |

### Standard Response Envelope

Successful responses return the resource directly as a JSON object:

```json
{
  "name": "maven-central",
  "format": "maven2",
  "type": "proxy",
  "url": "https://repo.example.com/repository/maven-central",
  "online": true
}
```

### HTTP Methods

| Method | Usage |
|--------|-------|
| `GET` | Retrieve a resource or list of resources |
| `POST` | Create a new resource |
| `PUT` | Update an existing resource (full replacement) |
| `DELETE` | Remove a resource |

### Response Status Codes (Success)

| Status Code | Description |
|-------------|-------------|
| `200 OK` | Request succeeded; resource returned in body |
| `201 Created` | Resource created successfully |
| `204 No Content` | Request succeeded; no response body (e.g., DELETE) |

## Pagination

List endpoints support pagination with the following parameters:

### Query Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `page` | integer | `1` | Page number (1-indexed) |
| `per_page` | integer | `20` | Items per page (maximum: `100`) |
| `continuation_token` | string | — | Opaque cursor token for continuation-based pagination |

### Paginated Response Format

```json
{
  "items": [
    { "...": "..." }
  ],
  "page": 1,
  "per_page": 20,
  "total": 142,
  "continuation_token": "eyJwYWdl..."
}
```

### Pagination Notes

- The `items` array contains the page of results.
- `total` indicates the total number of matching items across all pages.
- `continuation_token` is provided when there are more results available. Pass it as a query parameter in the next request to retrieve the following page.
- When using `continuation_token`, the `page` parameter is ignored.
- Maximum `per_page` value is `100`. Values above this are clamped to `100`.

## Error Handling

All API errors return structured JSON responses with appropriate HTTP status codes.

### Error Response Format

```json
{
  "error": "authentication_error",
  "message": "Invalid credentials provided",
  "status": 401,
  "details": {}
}
```

| Field | Type | Description |
|-------|------|-------------|
| `error` | string | Machine-readable error type identifier |
| `message` | string | Human-readable error description |
| `status` | integer | HTTP status code |
| `details` | object | Additional context (validation errors, field-level details) |

### HTTP Status Codes

| Status Code | Error Type | Description |
|-------------|-----------|-------------|
| `400` | `client_error` | Malformed request, validation failure, invalid parameters |
| `401` | `authentication_error` | Invalid credentials, expired token, missing authentication |
| `403` | `authorization_error` | Insufficient permissions, RBAC denial |
| `404` | `not_found` | Resource does not exist |
| `409` | `conflict` | Duplicate resource, optimistic lock failure |
| `500` | `system_error` | Unexpected internal server failure |
| `500` | `configuration_error` | Invalid system configuration state |
| `500` | `blobstore_error` | BlobStore operation failure |

### Error Categories

Errors are classified into four categories matching the original system's exception hierarchy:

1. **Client Errors (4xx)** — Invalid input from the API consumer. Includes malformed JSON, missing required fields, invalid parameter values, and resource conflicts.
2. **Security Errors (4xx)** — Authentication failures (`401`) and authorization denials (`403`). Authentication is always evaluated before authorization.
3. **System Errors (5xx)** — Unexpected internal failures such as unhandled exceptions, database connectivity issues, or out-of-memory conditions.
4. **Configuration Errors (5xx)** — Invalid configuration state such as missing required settings, incompatible BlobStore configuration, or failed startup phase validation.

### Validation Error Example

For requests that fail input validation, the `details` field contains field-level error information:

```json
{
  "error": "client_error",
  "message": "Request validation failed",
  "status": 400,
  "details": {
    "name": ["Repository name is required"],
    "format": ["Invalid format. Must be one of: maven2, npm, docker, nuget, pypi, apt, raw"]
  }
}
```

## Format-Native Protocol Endpoints

In addition to the REST management API, the server exposes format-native protocol endpoints for direct integration with build tools and package managers:

| Format | Base Path | Protocol | Client Tools |
|--------|-----------|----------|-------------|
| Maven | `/repository/{name}/**` | Maven Repository Layout | Maven CLI, Gradle |
| npm | `/repository/{name}/**` | npm Registry Protocol | npm, yarn |
| Docker | `/v2/{name}/**` | Docker Registry HTTP API V2 | docker CLI |
| NuGet | `/repository/{name}/index.json` | NuGet V3 Protocol | dotnet CLI, NuGet |
| PyPI | `/repository/{name}/simple/**` | PEP 503 Simple Repository API | pip |
| APT | `/repository/{name}/**` | Debian Repository Format | apt-get |
| Raw | `/repository/{name}/**` | Generic HTTP | curl, wget |

Each format supports three repository types:

- **Hosted** — Local artifact storage with direct upload.
- **Proxy** — Cache for a remote upstream repository with configurable TTL.
- **Group** — Virtual aggregation of multiple repositories.

See [repositories.md](repositories.md) for detailed endpoint documentation for each format, including request/response examples and format-specific features.

## Live API Documentation

### OpenAPI 3.x Specification

The application provides a machine-readable OpenAPI 3.x specification generated automatically by flask-smorest from Flask route decorators:

- **OpenAPI JSON:** `GET /swagger.json`
- **Swagger UI:** `GET /swagger-ui` (when the flask-smorest Swagger UI is enabled)

The OpenAPI specification replaces the original Swagger 2.2.20 integration and includes all management API endpoints with request/response schemas, parameter descriptions, and authentication requirements.

### Using the OpenAPI Specification

```bash
# Download the OpenAPI spec
curl -o openapi.json https://nexus.example.com/swagger.json

# Generate a client SDK (using OpenAPI Generator)
openapi-generator generate -i openapi.json -g python -o nexus-client/
```

## Monitoring Endpoints

The following endpoints provide system observability and are documented in detail in [admin.md](admin.md):

| Endpoint | Authentication | Description |
|----------|---------------|-------------|
| `/service/metrics` | Not required | Prometheus metrics in text exposition format |
| `/service/rest/v1/status/check` | Not required | Health check with component status details |
| `/service/rest/v1/status` | Not required | Simple availability indicator |

### Prometheus Metrics

The `/service/metrics` endpoint exposes application metrics in Prometheus text exposition format. Tracked metrics include:

- `http_requests_total` — Total HTTP request count by method, path, and status code.
- `http_request_duration_seconds` — Request latency histogram.
- `blob_operations_total` — BlobStore operation count by type (store, get, delete).
- `auth_attempts_total` — Authentication attempt count by realm and result.
- `active_repositories_count` — Number of currently active repositories.
- `scheduler_executions_total` — Scheduled task execution count by type and status.

### Health Check

The `/service/rest/v1/status/check` endpoint returns the aggregated health status of all system components (database, BlobStore, scheduler, search). This endpoint is designed to remain available even when other application endpoints are experiencing failures, making it suitable for load balancer health probes and Kubernetes liveness/readiness checks.

See [admin.md](admin.md) for the full health check response format and component details.
