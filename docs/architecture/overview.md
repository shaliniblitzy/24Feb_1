# Sonatype Nexus Repository — Architecture Overview

This document provides a comprehensive architecture overview of the Python/Flask reimplementation of the Sonatype Nexus Repository Manager backend server. The system has been completely rewritten from the original Java 21 / embedded Jetty 12.0.5 / RESTEasy 6.2.7 / Apache Shiro 2.0.0 / OSGi-Karaf 4.4.4 modular monolith into a modern Python 3.12+ application built on Flask 3.1.3.

The purpose of this document is to provide developers and architects with a thorough understanding of the system's structure, design decisions, component relationships, and the rationale behind the technology choices made during the migration. It serves as the primary architectural reference for onboarding, code reviews, and future extension of the platform.

---

## Layered Architecture

The application follows a five-layer architecture that mirrors the original Java system's design while leveraging Python-native frameworks and conventions. Each layer has a clear responsibility boundary, and dependencies flow strictly downward — upper layers depend on lower layers, never the reverse.

```
┌─────────────────────────────────────────────────┐
│                   API Layer                      │
│         (Flask Blueprints + flask-smorest)        │
├─────────────────────────────────────────────────┤
│                 Service Layer                    │
│           (Business Logic Services)              │
├─────────────────────────────────────────────────┤
│               Repository Layer                   │
│          (Hosted / Proxy / Group Logic)           │
├─────────────────────────────────────────────────┤
│                Storage Layer                     │
│        (File BlobStore / S3 BlobStore)            │
├─────────────────────────────────────────────────┤
│                  Data Layer                      │
│     (SQLAlchemy ORM — SQLite / PostgreSQL)        │
└─────────────────────────────────────────────────┘
```

### API Layer

The API Layer is implemented using Flask Blueprints combined with flask-smorest 0.45.0, replacing the original RESTEasy 6.2.7 JAX-RS resource classes. Every JAX-RS resource class from the Java implementation maps to a Flask Blueprint with equivalent route handlers, preserving all public REST API contracts including endpoint paths, HTTP methods, request/response schemas, and status codes.

All API Blueprint modules are located in `src/app/api/`:

| `components.py` | Component upload, download, and delete endpoints | F-501-RQ-002 |
| `assets.py` | Asset operations endpoints (metadata, download, delete) | F-501-RQ-002 |
| `users.py` | User CRUD endpoints (create, update, delete, list, status) | F-501-RQ-003 |
| `roles.py` | Role and privilege management endpoints | F-501-RQ-003 |

OpenAPI/Swagger documentation is auto-generated by flask-smorest and is accessible at the `/api/docs` endpoint, providing interactive API exploration for developers and client integrations.

JSON serialization and deserialization is handled by Marshmallow 3.23.2 schemas defined in `src/app/schemas/`, replacing Jackson 2.16.1. Each API resource has a corresponding Marshmallow schema that defines request validation rules and response serialization formats.

### Service Layer

The Service Layer is implemented as Python service classes in `src/app/services/`, replacing the Java service components from the original system. This layer encapsulates all business logic and is strictly separated from the route handlers in the API Layer, ensuring that business rules are reusable, testable, and independent of the HTTP transport.

Key service modules include:

| Module | Description | Replaces |
|---|---|---|

| `upload_manager.py` | Artifact upload handling with format-specific validation | `UploadManagerImpl.java` |
| `proxy_service.py` | Proxy fetch with caching, negative cache, and remote error handling | `HttpClientFacetImpl.java` + `ProxyFacetSupport.java` |
| `group_service.py` | Ordered member resolution for group repositories | Group facet resolution logic |
| `search_service.py` | Search indexing and query execution against Elasticsearch | Elasticsearch integration (F-103) |

| `support_zip_service.py` | Diagnostic bundle generation with credential sanitization | Support ZIP (F-403) |

### Repository Layer

The Repository Layer implements repository type logic for the three supported repository types in `src/app/repositories/`, replacing the OSGi bundle facets from the original Java system. Each repository type has distinct artifact resolution and storage strategies:

- **Hosted** (`hosted.py`): Serves artifacts directly from local BlobStore storage. Supports artifact upload, deletion, and browsing. Hosted repositories are the primary storage tier where artifacts are published by build tools and CI/CD pipelines.

- **Proxy** (`proxy.py`): Caches artifacts fetched from remote upstream repositories. Implements negative caching with a configurable time-to-live (TTL) to avoid repeated failed lookups. Uses the `requests` library (2.32.3) for outbound HTTP communication, replacing Apache HttpClient 4.5.14 from the Java implementation. Proxy repositories enable transparent access to public registries (Maven Central, npmjs.org, Docker Hub, etc.) while providing local caching for performance and reliability.

- **Group** (`group.py`): Aggregates multiple member repositories (Hosted, Proxy, or other Groups) into a single virtual repository. Resolves artifact requests by iterating through members in configured priority order, returning the first successful match. Group repositories provide a unified access point that simplifies client configuration.

Additional modules in this layer include:

- `facets.py` — Shared repository behavior abstractions and cross-cutting concerns common to all repository types
- `lifecycle.py` — Repository state machine implementing state transitions (NEW → STARTED → STOPPED), replacing the Java `StateGuard` pattern for safe lifecycle management

### Storage Layer

The Storage Layer implements the pluggable BlobStore abstraction in `src/app/storage/`, replacing the Java BlobStore subsystem. The layer uses the Strategy pattern with an abstract `BlobStore` interface and two concrete implementations:

- **File BlobStore** (`file_blobstore.py`): Local filesystem storage with atomic writes (temporary staging followed by rename-on-commit), soft-delete support for safe blob removal, and metadata sidecar files that store blob properties alongside the binary content. This is the default storage backend for standalone deployments. *(Feature F-201)*

- **S3 BlobStore** (`s3_blobstore.py`): AWS S3 cloud storage using `boto3` 1.36.7. Supports Server-Side Encryption (SSE) for data-at-rest protection, multipart uploads for large artifacts exceeding 5 MB, and configurable bucket/prefix organization. This backend enables scalable, durable storage for enterprise and cloud-native deployments. *(Feature F-202)*

The abstract base class in `blobstore.py` defines the contract that all BlobStore implementations must satisfy, including operations for creating, reading, deleting, and listing blobs, as well as metadata management.

The `maintenance.py` module provides BlobStore maintenance operations including compaction (reclaiming space from soft-deleted blobs), temporary file cleanup, and integrity checks that verify blob checksums against stored metadata. *(Feature F-203)*

### Data Layer

The Data Layer is implemented using SQLAlchemy 2.0.36 ORM with Flask-SQLAlchemy 3.1.1 integration, replacing the MyBatis 3.5.15 mappers and HikariCP 4.0.3 connection pooling from the original Java system.

The system supports a dual-database architecture:

- **SQLite** — Used for standalone and development deployments, providing zero-configuration setup. Replaces H2 2.3.232 from the Java stack.
- **PostgreSQL** — Used for clustered and enterprise deployments, providing full ACID compliance, concurrent access, and horizontal scalability. Connected via `psycopg2-binary` 2.9.10, replacing JDBC 42.7.2.

SQLAlchemy abstracts both database backends through a unified ORM layer, allowing the same application code to run against either database without modification.

All 14 SQLAlchemy models are defined in `src/app/models/`:

Database schema migrations are managed by Alembic with Flask-Migrate 4.0.7 integration (replacing Flyway 8.5.13), with migration scripts stored in the `migrations/` directory.

## Design Patterns

The following design patterns are applied throughout the codebase, each chosen to mirror the architectural intent of the original Java implementation while leveraging Python-native idioms:

| Pattern | Implementation | Replaces (Java) |
|---|---|---|
| **Application Factory** | `src/app/factory.py` — `create_app()` function creates and configures the Flask application instance | `Launcher.java` + Karaf bootstrap sequence |
| **Blueprint/Module** | Each feature area is registered as a separate Flask Blueprint for module isolation | OSGi bundles with independent lifecycle management |
| **Repository Pattern** | SQLAlchemy models paired with service classes provide data access abstraction per entity | DataStore API implemented with MyBatis mappers |
| **Service Layer** | Dedicated service classes in `src/app/services/` encapsulate business logic | Java service components with Guice injection |
| **Strategy Pattern** | Abstract `BlobStore` base class in `src/app/storage/blobstore.py` with File and S3 implementations | BlobStore interface with pluggable File and S3 backends |
| **Chain of Responsibility** | `src/app/auth/authentication.py` — multi-realm authentication iterating through realms until first success | Apache Shiro realm chain with `FirstSuccessfulModularRealmAuthenticator` |
| **Observer Pattern** | Blinker signals in `src/app/events/` for decoupled event dispatch to subscribers | Guava EventBus with annotated subscriber methods |
| **State Machine** | `src/app/repositories/lifecycle.py` — Repository state transitions (NEW → STARTED → STOPPED) | Java `StateGuard` for safe lifecycle transitions |
| **Factory Pattern** | Format handler factory creates repository instances with format-specific configuration | Repository recipes for format-aware repository creation |
| **Facade Pattern** | `src/app/services/repository_manager.py` — unified interface for all repository operations | `RepositoryManagerImpl.java` aggregating multiple subsystems |

## Authentication Architecture

The authentication system implements a multi-realm authentication chain that replaces Apache Shiro 2.0.0. The core design follows the Chain of Responsibility pattern, equivalent to the original `FirstSuccessfulModularRealmAuthenticator`.

### Authentication Chain

The authentication chain is implemented in `src/app/auth/authentication.py`. When a request arrives, the chain iterates through all configured authentication realms in order. Each realm examines the request for credentials it can handle (e.g., Basic auth header, Bearer token, JWT, etc.). Processing stops at the first realm that successfully authenticates the request, and the authenticated user principal is attached to the request context.

The five authentication realms are located in `src/app/auth/realms/`:

1. **Local Realm** (`local_realm.py`) — Authenticates users via username and password against locally stored credentials in the database. Passwords are securely hashed using modern algorithms. Replaces the Java `AuthenticatingRealmImpl`.

2. **Bearer Token Realm** (`bearer_token_realm.py`) — Authenticates requests using API keys transmitted via the `X-NuGet-ApiKey` header or the standard `Authorization: Bearer <token>` header. API keys are stored as hashed values in the database. Replaces the Java `BearerTokenRealm`.

3. **JWT Realm** (`jwt_realm.py`) — Validates JSON Web Tokens using PyJWT 2.10.1. Supports configurable token expiration, issuer validation, and audience verification. Replaces the Java `JwtSecurityFilter`.

4. **LDAP Realm** (`ldap_realm.py`) — Integrates with LDAP and Active Directory servers using `python-ldap` 3.4.4. Supports bind authentication, user search, group mapping, and TLS-secured connections. Replaces the Shiro LDAP realm configuration.

5. **SSO Realm** (`sso_realm.py`) — Provides SAML 2.0 and OpenID Connect (OIDC) federation support for single sign-on integration with enterprise identity providers. Replaces the security plugin SAML/OIDC functionality.

### Authorization Model

The authorization system implements a three-tier Role-Based Access Control (RBAC) model in `src/app/auth/authorization.py`:

- **Tier 1 — System-wide Privileges**: Global privileges that apply across the entire system (e.g., `nx-all`, `nx-repository-admin`, `nx-settings-read`). Administrators with system-wide privileges can manage all repositories and system settings.

- **Tier 2 — Repository-scoped Privileges**: Per-repository privileges that control access to specific repositories. Operations include `read`, `browse`, `edit`, `delete`, and `add`, each scoped to a specific repository or repository format.

- **Tier 3 — Sub-repository (CSEL) Privileges**: Content Selector Expressions (CSEL) provide fine-grained, path-based access control within repositories. CSEL expressions are evaluated against artifact paths and metadata to determine access at the individual component or asset level.

Supporting modules:

- `src/app/auth/rbac.py` — Core RBAC enforcement logic that evaluates user roles and privileges against requested operations
- `src/app/auth/content_selector.py` — CSEL expression parsing and evaluation engine for sub-repository access control
- `src/app/auth/password_utils.py` — Secure password hashing utilities using the `cryptography` 44.0.0 library (replaces BouncyCastle 1.78.1)

## Event System

The event system uses Blinker 1.9.0 signals to replace the Guava EventBus from the Java implementation, providing decoupled, publish-subscribe event dispatch throughout the application.

The implementation resides in `src/app/events/`:

- `event_bus.py` — Central event dispatcher that defines named Blinker signals and provides convenience methods for emitting events
- `event_types.py` — Enumeration of all event types including audit events, repository lifecycle transitions, component changes, asset modifications, and security events
- `subscribers.py` — Event subscriber registrations that connect event signals to handler functions

Key features powered by the event system:

| Feature | Description | Reference |
|---|---|---|
| **Audit Logging** | All security events (login, logout, permission changes) and data modification events (create, update, delete) are captured as audit log entries | F-303 |
| **Webhook Dispatch** | Configured events trigger HTTP POST callbacks to external endpoints with signed payloads | F-503 |
| **Configuration Propagation** | System configuration changes are broadcast to all dependent components for live reloading | F-404 |
| **Cleanup Triggers** | Repository events (upload, delete) trigger cleanup policy evaluation for affected repositories | F-204 |

## Format Handler Architecture

The format handler architecture provides plugin-based support for multiple repository formats in `src/app/formats/`. Each format implements its native protocol endpoints alongside the unified REST API, enabling build tools and package managers to interact with repositories using their standard protocols.

The abstract base class in `base.py` defines the format handler contract (Feature F-504), specifying the interface that all format implementations must satisfy. This includes methods for artifact upload, download, metadata resolution, search indexing, and cleanup rule evaluation.

### Supported Formats

| Format | Package | Protocol | Feature |
|---|---|---|---|
| **Maven** | `maven/` | Maven repository protocol — POM parsing, GAV coordinate resolution, `maven-metadata.xml` generation, checksum validation (MD5, SHA-1, SHA-256) | F-101-RQ-001 |
| **npm** | `npm/` | npm registry protocol — `package.json` metadata handling, tarball serving, scoped package support | F-101-RQ-004 |
| **Docker** | `docker/` | Docker Registry API v2 — manifest and layer operations, content-addressable storage, multi-architecture image support | F-101-RQ-005 |
| **NuGet** | `nuget/` | NuGet V3 API — service index, package metadata, content download, search endpoints | F-101-RQ-006 |
| **PyPI** | `pypi/` | PEP 503 Simple Repository API — simple index pages, package file serving, metadata extraction | F-101-RQ-007 |
| **APT** | `apt/` | Debian package index — Packages file generation, Release file signing, GPG signature validation | F-101-RQ-003 |
| **Raw** | `raw/` | Arbitrary binary file handling with automatic MIME type detection based on file extension and content | F-101-RQ-002 |

Each format handler supports all three repository types (Hosted, Proxy, and Group), adapting its behavior based on the repository context. Format handlers are registered as Flask Blueprints during application startup and serve format-native protocol endpoints at format-specific URL prefixes alongside the unified REST API in `src/app/api/`.

## Dual Database Strategy

SQLAlchemy 2.0.36 provides the abstraction layer for the dual-database architecture, allowing the application to run seamlessly against either SQLite or PostgreSQL depending on the deployment context:

- **SQLite** — Used for standalone and development deployments, providing a zero-configuration embedded database. This replaces H2 2.3.232 from the Java stack and requires no external database server.

- **PostgreSQL** — Used for clustered and enterprise deployments, connected via `psycopg2-binary` 2.9.10. PostgreSQL provides full ACID compliance, concurrent multi-user access, row-level locking, and support for horizontal scaling with read replicas.

The database backend is selected via the `DATABASE_URL` environment variable:

```bash
# SQLite (standalone/development)
DATABASE_URL=sqlite:///data/nexus.db

# PostgreSQL (clustered/enterprise)
DATABASE_URL=postgresql://user:password@host:5432/nexus
```

SQLAlchemy's built-in connection pooling replaces HikariCP 4.0.3, with pool size and overflow settings configurable through environment variables or configuration files.

Database schema migrations are managed by Alembic with Flask-Migrate 4.0.7 integration, replacing Flyway 8.5.13. Migration scripts in `migrations/versions/` track all schema changes and support both upgrade and downgrade operations.

### Configuration Profiles

The application provides three configuration profiles that set database and runtime defaults appropriate for each deployment context:

| Profile | File | Database | Debug Mode | Use Case |
|---|---|---|---|---|
| Development | `config/development.py` | SQLite (local file) | Enabled | Local development and debugging |
| Production | `config/production.py` | PostgreSQL | Disabled | Production and clustered deployments |
| Testing | `config/testing.py` | SQLite (in-memory) | Enabled | Automated test execution with fast teardown |

## Deployment Model

Gunicorn 25.1.0 serves as the production WSGI HTTP server, replacing the embedded Jetty 12.0.5 servlet container from the Java implementation. Gunicorn uses a pre-fork worker model for handling concurrent requests efficiently.

### Deployment Options

**Development:**

```bash
python run.py
# or
flask run
```

Uses the Flask built-in development server with debug mode, auto-reloading, and interactive debugger. Suitable for local development only — not for production use.

**Production:**

```bash
gunicorn -c gunicorn.conf.py wsgi:app
```

Uses Gunicorn with configurable worker processes, connection handling, and logging. The pre-fork model spawns multiple worker processes to handle concurrent requests, with each worker running an independent copy of the Flask application.

**Docker:**

```bash
docker-compose up
```

Orchestrates the full application stack with services for the Flask application, PostgreSQL database, and Elasticsearch search engine. The Docker deployment provides a consistent, reproducible environment across development, staging, and production.

### Key Deployment Files

| File | Description | Replaces |
|---|---|---|
| `wsgi.py` | WSGI entry point that creates the Flask application for Gunicorn | `Launcher.java` system entry point |
| `run.py` | Development server entry point with debug configuration | N/A (Java uses embedded Jetty) |
| `gunicorn.conf.py` | Gunicorn configuration (workers, bind address, timeout, access logging) | Jetty 12.0.5 server configuration |
| `Dockerfile` | Python 3.12 base image with Gunicorn and application dependencies | Docker Maven Plugin configuration |
| `docker-compose.yml` | Multi-service orchestration (Flask + PostgreSQL + Elasticsearch) | Deployment configuration |

For detailed deployment instructions including environment variable configuration, TLS setup, and production hardening, see `docs/deployment/guide.md`.

## Additional Components

### Scheduled Tasks

Background task scheduling is handled by APScheduler 3.10.4, replacing Quartz 2.3.2 from the Java stack. The implementation resides in `src/app/scheduler/`:

- `task_scheduler.py` — Core scheduler that manages job registration, execution, and lifecycle
- `task_registry.py` — Registry of available task types and their configuration schemas
- `task_logger.py` — Per-task logging that captures execution output and metrics (replaces `TaskLoggerHelper.java`)

The scheduler supports three trigger types:
- **One-time** — Tasks that execute once at a specified date/time
- **Interval** — Tasks that repeat at fixed intervals (e.g., every 6 hours)
- **Cron** — Tasks with cron expressions for complex scheduling patterns (e.g., daily at 2:00 AM)

Cluster-aware execution is supported for multi-node deployments, ensuring that scheduled tasks run on only one node at a time when using a shared job store backed by PostgreSQL. *(Feature F-402)*

### Health Checks and Monitoring

Application health monitoring and metrics collection reside in `src/app/monitoring/`:

- `health_checks.py` — Health check endpoints that verify database connectivity, BlobStore availability, Elasticsearch reachability, and scheduler status
- `metrics.py` — Application-level metrics collection (request counts, response times, active connections)
- `prometheus_exporter.py` — Prometheus-compatible metrics endpoint using `prometheus-client` 0.21.1

Request-level instrumentation is provided by `prometheus-flask-instrumentator`, which automatically captures HTTP request duration, status codes, and request sizes. This replaces Dropwizard Metrics 4.2.25 and the Java Prometheus Client 0.16.0. *(Feature F-401)*

### Search Integration

Full-text search capabilities are provided through Elasticsearch integration in `src/app/search/`:

- `elasticsearch_client.py` — Configured Elasticsearch Python client (`elasticsearch` 7.17.12), replacing the Java Elasticsearch client
- `index_manager.py` — Index lifecycle management including creation, mapping updates, and reindexing operations
- `query_builder.py` — Query construction utilities for component and asset search, supporting keyword search, format-specific filtering, and coordinate-based lookup

The search system indexes component metadata (name, namespace, version, format) and asset attributes (path, content type, checksums) for fast retrieval across large repositories. *(Feature F-103)*

### Webhook Integration

Webhook support enables external systems to receive real-time notifications about repository events. The implementation resides in `src/app/webhooks/`:

- `dispatcher.py` — Webhook delivery engine with configurable retry logic, exponential backoff, and delivery status tracking
- `payload_signer.py` — HMAC-SHA256 payload signing that allows webhook receivers to verify the authenticity and integrity of incoming payloads

Webhooks can be configured to trigger on specific event types (e.g., component upload, repository creation, security changes) and support filtering by repository, format, or event attributes. *(Feature F-503)*

### Plugin Architecture

The extension point framework in `src/app/plugins/` provides a structured mechanism for extending the application with custom functionality:

- `plugin_manager.py` — Plugin discovery, loading, validation, and lifecycle management. Plugins are discovered from a configurable directory and loaded dynamically at startup.
- `extension_points.py` — Defined extension points that plugins can implement, including custom format handlers, authentication realms, storage backends, and scheduled tasks.

The plugin architecture enables third-party extensions without modifying core application code, preserving the extensibility model of the original OSGi-based plugin system. *(Feature F-504)*

### SSL/TLS Certificate Management

Certificate management in `src/app/security/` provides tools for managing SSL/TLS certificates and cryptographic operations:

- `ssl_manager.py` — SSL context configuration, certificate loading, and TLS version management
- `certificate_store.py` — Trusted certificate store for managing CA certificates used by proxy repositories to connect to HTTPS upstream sources
- `crypto_utils.py` — Cryptographic utility functions for hashing, signing, and key generation

The implementation uses the `cryptography` 44.0.0 library, replacing BouncyCastle 1.78.1 from the Java stack. *(Feature F-302)*

### Scripting Support

Administrative scripting capabilities are provided by `src/app/services/script_service.py`, replacing the Groovy scripting engine from the Java implementation. Python's native scripting capabilities are used instead:

- Scripts are stored in the database with metadata (name, type, content)
- Execution runs in a sandboxed environment with controlled access to application services
- Script results and output are captured and returned to the caller

Sandboxed execution ensures that administrative scripts cannot compromise system security or stability. *(Feature F-502)*

## Performance Targets

The following performance targets are preserved from the original Java system and must be achieved by the Python/Flask implementation:

| Metric | Target | Measurement Context |
|---|---|---|
| REST API Response Time | < 500 ms average | Across all REST API endpoints under normal load |
| Cached Artifact Resolution | < 200 ms | Retrieval of previously cached artifacts from BlobStore |
| Full-Text Search (100K components) | < 2 seconds | Elasticsearch query over 100,000 indexed components |
| System Uptime | ≥ 99.9% | Annual availability target for production deployments |
| Storage Efficiency (deduplication) | > 2:1 ratio | Logical-to-physical storage ratio with content deduplication |

These targets inform architectural decisions including connection pooling configuration, caching strategies, query optimization, and BlobStore performance tuning.
